# Sensor automations — 261029_convenience

## 사용 위치

**Settings → Convenience & Macros → Automations**.
Juniper **Body + Chassis**에서 실행하는 로컬 자동화 엔진입니다.
브라우저나 Home Assistant 서버가 없어도 동작하며 Home Assistant 연동 기능은 아닙니다.
모든 규칙은 기본 OFF입니다. 최대 16개 규칙을 각각 저장하고 켜거나 끌 수 있습니다.
규칙을 한 번 작성해 저장한 다음 **Saved rules · enable or disable** 목록의 토글로
즉시 활성화/비활성화합니다. 비활성화해도 센서·조건·지연·동작은 보존되며 재부팅 후에도 유지됩니다.
편집 중에는 목록 토글을 잠가 저장되지 않은 변경과 혼동하지 않도록 합니다.

규칙은 센서 조건, 추가 기어 조건, 진입/이탈 지연, 실행 시점, 동작으로 구성합니다.

| 설정 | 지원 범위 |
| --- | --- |
| 속도 | 최소·최대 0–150 km/h, 양 끝값 포함, 설정은 1 km/h 단위 |
| 기어 | P / R / N / D |
| 브레이크 | Released / Pressed |
| 추가 조건 | 특정 기어 또는 Any |
| 진입·이탈 지연 | 각각 0–30,000 ms |
| 실행 시점 | 조건이 참이 될 때 또는 거짓이 될 때 |
| 동작 | 자동 종료가 있는 카메라, 기존 공통 기능 액션 목록 |

기어·브레이크는 화면에서 상태를 선택하며, 속도는 범위를 입력합니다.
기존 기능 액션은 BLE/매크로와 같은 지원 여부 검증 및 유효기간 1초의 제한된 큐를 사용합니다.
토글 액션은 실행할 때 현재 설정을 반전합니다. 한 조건을 유지하는 동안 반복 실행하지 않습니다.
CAN Transmission을 끄는 액션을 실행하면 자동화도 중단되므로 자동화로 스스로 다시 켜지지 않습니다.

설정은 기존 편의 기능과 별개인 `features/automation_v2`의 버전 2, 208바이트 레코드에 저장합니다.
한 규칙의 전체 필드를 원자적으로 저장하며 저장 실패 시 기존 설정을 유지합니다.
이전 4개 규칙의 `features/automation` 레코드는 설정과 활성 상태를 그대로 읽어 오며,
처음 저장할 때 새 형식으로 저장합니다. 손상된 새 레코드가 있으면 과거 설정을 되살리지 않습니다.
부팅, 설정 저장, 입력 단절 후 복구에서는 첫 정상값을 기준 상태로 삼습니다.
그 뒤 새 조건 전이가 발생해야 실행하므로, 부팅 당시 이미 조건을 만족한다고 즉시 실행하지 않습니다.
설정 저장과 활성화/비활성화는 **변경한 규칙만** 대기 상태를 초기화합니다. 다른 규칙은 계속 실행합니다.
현재 활성 카메라 규칙을 변경하거나 비활성화하면 카메라 자동 종료 권한을 해제하며 카메라를 임의로 닫지 않습니다.

## 저속 카메라

1. 규칙을 선택하고 **Low-speed camera preset**을 누릅니다.
2. 기본값은 **D, 1–20 km/h, 진입 지연 0 ms, 이탈 지연 3,000 ms**입니다.
3. 필요하면 속도 범위와 지연을 바꾸고 **Enable rule → Save rule**을 선택합니다.

카메라는 최대 한 규칙에서만 자동 제어할 수 있습니다. 카메라 액션은 속도 조건,
D, Becomes true 조합을 사용합니다. 다른 기어는 차량의 기본 카메라 제어에 맡깁니다.

범위에 진입했을 때 카메라가 OFF로 확인되면 카메라 버튼의 soft press를 요청합니다.
전송 성공만으로 켜졌다고 간주하지 않습니다. 요청 이후 카메라 활성 상태가 수신되어야
해당 규칙이 켠 것으로 기록합니다. 버튼 요청은 최신 순정 프레임의 카메라 필드만 바꾸고,
100 ms 후 다음 정상 프레임에서 release를 요청합니다. 화면 반응 확인 제한은 1.5초입니다.

범위를 이탈한 상태가 설정된 시간만큼 지속되면, 이 규칙이 켠 카메라만 종료를 요청합니다.
지연 중 범위로 돌아오면 종료를 취소합니다. 정지하여 최소 속도 아래로 내려가도 이탈입니다.
종료 송신 직전 범위로 돌아온 경우에도 요청을 취소합니다.

다음 경우 자동 종료 권한을 해제하고 카메라를 임의로 토글하지 않습니다.

- 시작 전 이미 켜져 있던 카메라 또는 최초 송신 직전 수동으로 켜진 카메라
- 물리 카메라 버튼 조작, 카메라가 꺼진 상태 수신, D 이탈(후진 포함)
- 속도·기어·화면 상태·버튼 원본의 오래되거나 유효하지 않은 입력
- CAN Listen Only, 컨트롤러 복구, 프로필·설정 변경, AP/NAG 입력 제어와 충돌
- 송신 실패 또는 켜짐 확인 시간 초과

실패한 요청은 자동 재시도하지 않습니다. 새 조건 전이가 있어야 다시 시도합니다.
차량 카메라 버튼은 절대 ON/OFF 명령이 아닌 토글이므로, 물리 버튼/화면 전이로
관측할 수 없는 동시 터치 조작의 원인까지 식별할 수는 없습니다.

## 후진 비상등

**Convenience & Macros → Reverse Hazard**를 켭니다.
기존 기능을 유지하며, R 진입 시 기존 점멸이 없는 상태에서 시작하고 R 이탈 시 종료합니다.
수동 비상등 버튼 조작, 알람/충돌 등 다른 점멸 요청은 자동 제어를 해제합니다.
R 이탈 시에는 최근 상태가 BUTTON 요청으로 확인되고 자동 제어 권한이 있을 때만
OFF 토글을 허용합니다. 부팅 당시 R인 상태만으로는 새 진입으로 취급하지 않습니다.
**Hazard Light · 3 Flashes**는 별도의 단발 동작이며 후진 중에는 실행할 수 없습니다.

## CAN 신호와 검증 범위

첨부 Bayberry VEH DBC에 맞춰 사용합니다. 기존 다른 차량용 속도 디코더와 위치가 다릅니다.

| 입력/요청 | CAN / 필드 |
| --- | --- |
| 속도 | `0x257 DI_vehicleSpeed`, bit 43, 13비트, `raw × 0.08 − 40 km/h`, SNA=8191 |
| 기어 | `0x118 DI_gear`, bit 21, 3비트 |
| 브레이크 | `0x39D IBST_driverBrakeApply`, bit 16, 2비트 |
| 카메라 활성 | `0x353 UI_cameraActive`, bit 41 |
| 전방 카메라 표시 | `0x294 UI_fasciaCameraShown`, bit 39 |
| 카메라 버튼 | `0x3C2` MUX1, `VCLEFT_swcCameraButtonState`, bit 50, 2비트 |

카메라 화면 상태 두 신호가 모두 최근 1초 이내에 수신되어야 하며, 어느 하나라도 ON이면
이미 켜진 것으로 봅니다. 속도·기어·브레이크 조건의 유효시간은 500 ms,
카메라 버튼 원본은 150 ms입니다. 합성 카메라 press의 수신 에코는 순정 입력 캐시에 넣지 않습니다.

호스트 테스트는 진입/이탈 지연, 재진입, 입력 단절·복구, 타이머 래핑, NVS 실패,
엄격한 API 파싱, 기존 카메라 보존, 수동 개입, 최종 송신 경합, 버스 분리를 검사합니다.
브라우저 테스트는 소스/내장 HTML 양쪽의 프리셋, 규칙 편집·저장, 편집 중 폴링,
실패 복구와 모바일 폭을 검사합니다. DBC 검증은 총 82개 필드를 대조합니다.

**실차 검증은 아직 하지 않았습니다.** 특히 soft press/release로 해당 카메라 화면이
토글되는지, 두 화면 상태 신호의 의미·주기, 3초 종료 및 수동·후진 전환 동작을 확인해야 합니다.
송신 성공과 DBC 필드 일치는 차량의 명령 수락 또는 물리 동작을 증명하지 않습니다.

## AP 회귀 테스트 실패의 의미

`test_v328_continuous_ap_nag_host.py`는 Body 경로 검사 이후 Party+Chassis 경로에서
오래된 우측 휠 누름 프레임을 NAG 송신 함수에 넘기고, Continuous AP가 새 중립 프레임으로
교체하여 우측 누름 필드를 OFF(0x10)로 만들 것이라고 기대합니다.
현재 실제 펌웨어가 사용하는 `continuous_ap_fsm_pure.h`의 경로 정책은 Continuous AP를
Body CAN 경로에만 허용합니다. 따라서 해당 Party+Chassis 검사는 현재 지원 범위와 맞지 않습니다.
변경 전 e11c216에서도 같은 assertion이 실패합니다. 현재의 `test_continuous_ap_nag_host.py`는
지원되는 Body 경로의 입력 충돌 방지와, CAP 미지원 경로의 독립 NAG 송신을 검사하며 통과합니다.
이는 자동화 변경으로 AP가 고장났다는 결과가 아니며, 모든 실차 AP 동작을 검증했다는 의미도 아닙니다.
